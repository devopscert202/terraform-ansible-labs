Terraform 101 — the page before every other page

This page assumes you have never run Terraform, never seen a .tf file, and have no cloud experience. Every term is defined the first time it appears, and nothing later in the page is assumed earlier. Read it top to bottom once, then start Lab 00.

Two words are used constantly and are worth pinning down before anything else. A binary is a single ready-to-run program file; terraform is one file you download and put on your computer, not an application you install with a wizard. A CLI (command-line interface) is a program you drive by typing commands into a terminal instead of clicking buttons. Terraform is a CLI binary.

This track targets Terraform >= 1.5.0 and the AWS provider ~> 5.0, in region us-east-1. Section 9 explains exactly what those two version strings permit.
1 · The idea

What Terraform is

Terraform is an infrastructure as code tool. Infrastructure means the servers, networks, databases and permissions your software runs on. Infrastructure as code means you write those things down in text files, keep the files like any other source code, and let a program build the real thing from them.

Terraform is declarative: you describe the end result you want, and the tool works out the steps. The opposite is imperative, where you write the steps yourself and the end result is whatever the steps happen to produce. A shopping list is declarative; turn-by-turn driving directions are imperative.

The same job, three ways

ApproachHow you express itWhat happens on the second run
Web consoleYou click through forms in a browser to create one server.You click through them again, from memory, and get something slightly different. Nothing recorded what you did.
Shell scriptYou write aws ec2 run-instances ... — the exact command to create a server. Imperative.It creates a second server, because the script says "create", not "make sure one exists". You must hand-write the checks yourself.
TerraformYou write "there is one server, of this size, with these tags". Declarative.Nothing happens. Reality already matches the file, so there is nothing to do.

That last row is idempotence: running the same operation again produces the same end state instead of stacking up duplicates. It is the single most useful property Terraform gives you, and it is why the declarative style is worth learning.

A whole Terraform file

# main.tf

resource "random_pet" "example" {
  length = 2
}

That is a complete, valid configuration. It says: a random two-word name exists. It does not say how to generate one, when to generate one, or what to do if one already exists — Terraform decides all of that. The example deliberately creates nothing in any cloud, so it costs nothing and needs no account.

2 · The payoff

What it does for you

Every benefit below follows from one fact: your infrastructure is now a text file, and text files can be copied, compared, reviewed and deleted.

BenefitWhat it means in practice
RepeatabilityThe same files build the same environment in a test account and a production account. New joiners run one command instead of following a wiki page of screenshots.
ReviewA change to a firewall rule arrives as a change to a line of text. A colleague can read it, question it and approve it before it reaches the real network.
VersioningThe files live in version control, so you can see who changed the server size, when, and why, and you can go back to last week's definition.
TeardownOne command destroys everything the files created — and only that. Manually built environments linger for years because nobody is sure what is safe to delete.
A dry runTerraform can show you exactly what it intends to change before it changes anything. No web console offers that.
The dry run is the habit that separates confident Terraform users from nervous ones. Section 10 introduces the command that produces it.
3 · Provenance

Who owns Terraform, and what happened to its licence

Terraform was created by HashiCorp in 2014. HashiCorp is now a wholly owned subsidiary of IBM: IBM announced the acquisition on 24 April 2024 and completed it on 27 February 2025, at an enterprise value of 6.4 billion US dollars. The products kept their names, and the terraform binary is still published by HashiCorp.

The licence change

A licence is the legal document saying what you are allowed to do with someone else's code. From its first release up to and including version 1.5.7, Terraform used the Mozilla Public License 2.0 (MPL 2.0), a recognised open-source licence with essentially no restrictions on use. On 10 August 2023 HashiCorp announced that all future releases would move to the Business Source License 1.1 (BSL). That change took effect from Terraform 1.6.0.

BSL is source-available, not open-source: you can read and modify the code, but there is a restriction attached. The restriction is narrow. The additional use grant in Terraform's licence file permits production use outright, and only forbids offering Terraform to third parties on a hosted or embedded basis in a paid product that competes with IBM's own paid Terraform offerings. It states explicitly that using Terraform for internal purposes within an organisation is not a competitive offering. Each individual release reverts to MPL 2.0 four years after it was published.

What this means for you on this track: nothing. Learning Terraform, running it in a training account, and using it to manage your own employer's infrastructure are all permitted without payment. The restriction only bites if you sell a competing Terraform-based service.

Why OpenTofu exists

The licence change was unpopular with users who had built businesses around the previously open-source code. A group of companies and individuals published a manifesto asking for the change to be reverted; when it was not, they forked the project — took a copy of the last MPL 2.0 release, 1.5.7, and continued it independently. That fork is OpenTofu, accepted by the Linux Foundation on 20 September 2023, with OpenTofu 1.6 shipping in January 2024 as a drop-in replacement for Terraform 1.6.

OpenTofu is a separate project today with its own release schedule and some features Terraform does not have, but it still uses the same configuration language and the same state file format, and its command is tofu instead of terraform. Most material written for Terraform 1.x applies to it unchanged. This track teaches Terraform, so every command on these pages starts with terraform. You will hear the name OpenTofu; now you know what it is.

4 · Versions

Terraform version numbers, and which one this track wants

Terraform version numbers have three parts separated by dots — MAJOR.MINOR.PATCH, for example 1.16.0. This is the semantic versioning convention: the major number changes when something old stops working, the minor number changes when features are added, and the patch number changes for bug fixes only.

Terraform reached 1.0 in June 2021 and has stayed on major version 1 ever since, with a promise that configuration written for one 1.x release keeps working on later 1.x releases. In practice that means the gap between your version and this track's floor rarely matters, as long as yours is newer.

Ask your own installation

terraform version

Expected output

Terraform v1.14.8
on darwin_arm64

Your version of Terraform is out of date! The latest version
is 1.16.0.

The first line is your installed version. The second is the operating system and processor architecture the binary was built for. The third line appears only when a newer release exists — Terraform checks the public release index when you run this command.

VersionStatus
1.16.0The current release at the time this page was generated, published 26 August 2026. Verified against developer.hashicorp.com/terraform/install.
1.5.7The last MPL 2.0 release, and the point OpenTofu forked from. Also the last release before this track's floor.
>= 1.5.0What this track requires. Every lab is written against this floor. Anything from 1.5.0 upwards, including the current release, will work.
If your version is older than 1.5.0, download a newer one before Lab 00. If it is newer than 1.16.0 by the time you read this, that is fine — the floor is a minimum, not a target.

5 · The language

What HCL is, and the anatomy of a block

HCL is the HashiCorp Configuration Language — the language you write Terraform in. You put it in plain text files whose names end in .tf, and Terraform reads every .tf file in the directory you run it from and treats them as one configuration. File names carry no meaning to Terraform; main.tf is a convention, not a rule. HCL is built from just two things: blocks, which are named containers written with braces, and arguments, which are name-equals-value pairs inside them. The example below is one block, and the table names every part of it.

Example

resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.micro"

  tags = {
    Name = "tflabs-web"
    Lab  = "lab03"
  }
}

Line by line

LineWhat it does
resourceThe block type. It says what kind of thing this block declares. Terraform has a fixed set of block types: resource, data, variable, output, provider, terraform, locals, module.
"aws_instance"The first block label. For a resource block this is the resource type — the exact kind of real-world thing to create. The name is fixed by the provider, so you cannot invent it.
"web"The second block label: the local name. You choose this freely. It is how you refer to this block elsewhere in your own configuration, and it never appears in AWS.
{ ... }The body: everything between the braces. It holds arguments and sometimes nested blocks.
instance_typeAn argument name. Which arguments are valid, and which are required, is decided by the resource type.
"t3.micro"An argument value. Here a literal piece of text in double quotes.
data.aws_ami.al2023.idAlso an argument value, but an expression rather than a literal: it reads a value out of another block instead of stating one. Sections 6 and 7 cover expressions and data blocks.
tagsAn argument whose value is a group of key/value pairs in braces. Nesting is normal in HCL and the indentation is purely for humans.
How the parts become an address. The two labels combine into a reference address you use to point at this block from anywhere else: aws_instance.web.id means resource type aws_instance, local name web, attribute id — the instance ID that AWS assigns after creation. Blocks declared with data instead of resource take a data. prefix, which is why the AMI above is data.aws_ami.al2023.id and not aws_ami.al2023.id.

6 · The language

HCL basics: types, comments, references and formatting

Every argument value in HCL has a type. There are three simple types — string, number and bool — and three collection types — list, map and object. You will also write expressions: values computed from other values rather than typed out literally. Two blocks below are new: variable declares an input someone can set from outside, and locals names values used repeatedly inside the configuration. Both are covered properly later in the track; here they are just convenient places to show the types.

Example

# A comment starts with a hash. // also works for one line,
/* and this form spans
   several lines. */

variable "environment" {
  type        = string
  description = "Deployment environment name."
  default     = "dev"
}

locals {
  instance_count = 2                            # number
  enable_logging = true                         # bool
  zones          = ["us-east-1a", "us-east-1b"] # list of string

  # map of string
  common_tags = {
    Project = "tflabs"
    Env     = var.environment
  }

  name_prefix = "tflabs-${var.environment}-web" # interpolation: needed
  env_name    = var.environment                 # no interpolation: not needed
}

Line by line

LineWhat it does
# // /* */The three comment forms. Terraform ignores them. # is the conventional one and terraform fmt rewrites // to #.
type = stringA string is text in double quotes. Declaring the type makes Terraform reject a wrong value early with a clear error instead of a confusing one later.
2A number. Written bare, with no quotes. "2" would be a string that happens to contain a digit.
trueA bool — either true or false, lower case, no quotes.
[ ... ]A list: ordered values in square brackets, reached by position starting at zero, so local.zones[0] is "us-east-1a".
{ ... }A map: values reached by key rather than position, so local.common_tags["Project"] is "tflabs". An object is the same shape with a fixed set of keys whose types are declared individually.
var.environmentA reference. The address form is source, then name, then attribute: var.NAME for a variable, local.NAME for a local value, RESOURCE_TYPE.NAME.ATTRIBUTE for a resource.
"tflabs-${var.environment}-web"Interpolation: ${ } inside a quoted string means "evaluate this and paste the result here". Needed here because the value is glued between two pieces of literal text.
= var.environmentThe same value with no interpolation, because it is the whole value. Writing "${var.environment}" would work but is redundant, and Terraform warns about it.
Formatting is automatic. The = signs above line up in columns. Nobody does that by hand — running terraform fmt rewrites every .tf file in the directory to the canonical style: standard indentation, aligned equals signs, consistent comment markers. It changes layout only, never meaning. Run it before every commit, and use terraform fmt -check in automation to fail a build that was not formatted.

7 · Plugins

What a provider is

Terraform itself knows nothing about AWS. It does not know what an EC2 instance is, which API endpoint creates one, or how to authenticate. All of that lives in a provider.

A provider is a plugin — a separate program that Terraform downloads and runs alongside itself to add a capability it does not have built in. Each provider translates your HCL into calls against one specific API. The aws provider defines the resource types whose names begin aws_; the random provider defines random_pet and its siblings and talks to no API at all. There are thousands of others.

Where providers come from

The Terraform Registry at registry.terraform.io is the public catalogue Terraform downloads providers from. Every provider has a two-part source address, NAMESPACE/NAME. In hashicorp/aws, hashicorp is the namespace — the organisation that publishes it — and aws is the provider name. The namespace matters: it is what distinguishes the official AWS provider from a third party's fork of it. The registry is also where the documentation for every resource type lives, and it is the reference you will use most often once you start writing real configurations.

Where the plugin lands on your disk

You never download a provider by hand. The terraform init command reads your configuration, works out which providers it needs, fetches them, and unpacks them into a hidden .terraform directory next to your .tf files:

.terraform/
└── providers/
    └── registry.terraform.io/
        └── hashicorp/
            └── aws/
                └── 5.31.0/
                    └── darwin_arm64/
                        └── terraform-provider-aws_v5.31.0_x5

That last file is the provider binary. The path records the registry it came from, the namespace, the name, the exact version and the platform it was built for. The whole .terraform directory is disposable — it is rebuilt by terraform init and is never committed to version control, because it contains large platform-specific binaries rather than anything you wrote.

Provider version numbers are independent of Terraform's. AWS provider 5.31.0 has nothing to do with Terraform 1.16.0; they are different pieces of software on different release schedules.

8 · Plugins

How to add a provider, and why it takes two blocks

Adding a provider is always two separate declarations, and beginners reliably confuse them. The required_providers entry says which plugin to install and which versions are acceptable. The provider block says how to configure the plugin once it is installed. They are separate because they answer different questions at different times: Terraform must resolve and download the plugin before it can hand it any settings, and a configuration can install one plugin but configure it several times over — one AWS provider, configured for two regions, is a normal thing to want. Put both in a file and run terraform init to make it real.

Example

terraform {
  required_version = ">= 1.5.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

Line by line

LineWhat it does
terraform { }A block that configures Terraform itself rather than any infrastructure. It takes no labels, and a configuration has at most one of them.
required_versionThe versions of the Terraform CLI this configuration accepts. Terraform checks its own version against this and refuses to run if it does not match. It cannot upgrade itself.
required_providersThe declaration block: which plugins this configuration needs, where to get them, and which versions are acceptable.
aws = { ... }The local name for this provider inside your configuration. It is what makes aws_instance resolve to this provider.
sourceThe registry address, NAMESPACE/NAME. "hashicorp/aws" is the official AWS provider. Omitting source is a bug waiting to happen; always state it.
version = "~> 5.0"A version constraint: a rule saying which releases are acceptable. This one accepts any 5.x release — 5.0.1, 5.31.0, 5.99.0 — and refuses 6.0.0 and newer, and anything older than 5.0. Section 9 decodes every operator in full.
provider "aws"The configuration block: settings passed to the plugin once it is installed. Its label matches the local name declared above.
regionAn AWS-provider-specific setting. Every AWS resource in this configuration is created in us-east-1. Different providers take completely different settings.
The terraform block is the one place where you cannot use variables or expressions. Its contents must be literal values, because Terraform reads it before it has evaluated anything else.

9 · Version constraints

Every version constraint operator, and what each one really allows

A version constraint is a string that says which releases of something are acceptable. The same syntax is used in three places: required_version for Terraform itself, the version argument inside required_providers for a plugin, and the version argument on a module. Learn it once and it applies everywhere.

The syntax is an operator, a space, and a version number. Terraform installs the newest published version that satisfies every constraint that applies. If no published version satisfies them, it stops with an error rather than guessing.

ConstraintWhat the operator meansExactly which versions
= 5.31.0
5.31.0		Exactly one version. The operator is optional, so the bare number means the same thing. This is the only form that cannot be combined with other conditions, and the only form that will select a pre-release such as 6.0.0-beta1.Allows: 5.31.0 only.
Excludes: everything else, including 5.31.1 and 5.30.9.
!= 5.31.0Excludes one exact version. Used to skip a single known-bad release while staying open to the rest. Almost always paired with another condition.Allows: 5.30.9, 5.31.1, 6.0.0 — every published version except one.
Excludes: 5.31.0.
> 5.31.0Strictly newer than the stated version.Allows: 5.31.1, 5.32.0, 6.0.0, 7.4.2.
Excludes: 5.31.0 itself, and anything older.
>= 5.31.0The stated version or newer. The usual choice for a shared module, which should set a floor but not a ceiling.Allows: 5.31.0, 5.31.1, 6.0.0, 7.4.2.
Excludes: 5.30.9 and anything older.
< 6.0.0Strictly older than the stated version. A ceiling, normally used to stay off a major release that contains breaking changes.Allows: 5.99.0, 5.31.0, 1.0.0.
Excludes: 6.0.0 itself, and anything newer.
<= 6.0.0The stated version or older.Allows: 6.0.0, 5.99.0, 5.31.0.
Excludes: 6.0.1 and anything newer.
~> 5.0The pessimistic constraint. It allows the right-most component you wrote to increase, and nothing to its left. You wrote two components, so the right-most is the minor number: minor and patch may both rise, major may not.Allows: 5.0.0, 5.0.1, 5.1.0, 5.31.0, 5.99.9 — any 5.x.
Excludes: 6.0.0 and newer; 4.67.0 and older.
~> 5.1.2The same operator with three components, which means something genuinely different. The right-most is now the patch number, so only the patch may rise. This is the form to use when you want bug fixes and nothing else.Allows: 5.1.2, 5.1.3, 5.1.9, 5.1.40.
Excludes: 5.2.0 (minor rose), 5.1.1 (older), 6.0.0.
>= 5.20.0, < 6.0.0A compound constraint: several conditions in one string, separated by commas. A version must satisfy all of them. This is how you express a range that no single operator can.Allows: 5.20.0, 5.31.0, 5.99.9.
Excludes: 5.19.9, 6.0.0, 6.1.0.
>= 5.0.0, != 5.31.0, < 6.0.0Three conditions at once — a floor, a ceiling, and one bad release cut out of the middle. There is no limit on how many you combine.Allows: 5.0.0, 5.30.9, 5.31.1, 5.99.9.
Excludes: 4.99.0, 5.31.0, 6.0.0.
Pre-releases are special. A version with a dash suffix, such as 6.0.0-beta1, is never matched by >, >=, <, <= or ~>. To use one you must name it exactly with = or with no operator at all. This is why >= 5.0.0 will not quietly drag a beta into your build.

Two different things get versioned, and they are not the same

SettingConstrainsIf the constraint is not met
required_versionThe Terraform CLI binary on the machine running the command. One per configuration, inside the terraform block.Terraform refuses to run and tells you to change your Terraform installation. It cannot fix this itself — you download a different binary.
version in required_providersA provider plugin. One per provider. Completely independent of the Terraform version.terraform init downloads a version that does satisfy it. Terraform fixes this itself, automatically.

What the constraint permits, and what the lock file pins

A constraint describes a range. It does not decide anything on its own. The decision is recorded in a file called .terraform.lock.hcl, which terraform init creates in your working directory the first time it installs a provider.

# .terraform.lock.hcl  (generated by terraform init - do not hand-edit)

provider "registry.terraform.io/hashicorp/aws" {
  version     = "5.31.0"
  constraints = "~> 5.0"
  hashes = [
    "h1:cIUS0MSHV3JQyDb1UDXWvVHmp0IuZ8y7WPMSVJvhBg8=",
  ]
}
LineWhat it records
versionThe one exact release Terraform actually chose. This is the pin.
constraintsA copy of what your configuration asked for, kept so you can see why that version was chosen.
hashesChecksums of the downloaded package. On later runs Terraform verifies the file it fetched matches, so a tampered or substituted plugin fails loudly.

Once a version is recorded, terraform init re-selects that version on every subsequent run, even when a newer one exists inside the constraint. The only way to move it is terraform init -upgrade, which discards the recorded selection and picks the newest version the constraint still allows. Commit the lock file to version control: it is the difference between everyone on the team running the same plugin and everyone running whatever was newest on the day they cloned.

Why a colleague got a different provider version from the same repository. You cloned in March, ran terraform init against version = "~> 5.0", and got 5.31.0. Your colleague cloned in September and got 5.94.0. Both are correct: the constraint permits every 5.x, and each of you took the newest available on your own day. The lock file is what removes the ambiguity — if you had committed it, their terraform init would have installed 5.31.0 too. A constraint permits a range; the lock file records the choice.
The lock file covers providers only. It does not pin the Terraform CLI version, and it does not pin module versions — Terraform always takes the newest module version the constraint allows.

10 · The command line

The commands you will actually type

Terraform is one binary with subcommands. You run them from inside the directory that holds your .tf files, in roughly the order below. The first three are safe — they change nothing in any cloud.

CommandWhat it does
terraform initPrepares the directory: reads your configuration, downloads the providers it needs, and writes the lock file. Run it first, and again any time you add or change a provider.
terraform fmtRewrites your files into the canonical layout. Changes formatting only.
terraform validateChecks the configuration is internally consistent — no syntax errors, no unknown arguments, no references to blocks that do not exist. It does not contact any cloud, so it cannot tell you whether AWS will accept the request.
terraform planThe dry run. Compares what you asked for against what exists and prints the changes it would make. Changes nothing.
terraform applyMakes the changes. Shows the same plan first and waits for you to type yes. This is the command that creates real, billable resources.
terraform destroyDeletes everything this configuration created. Also asks for confirmation. Run it at the end of every lab so nothing keeps costing money.
terraform outputPrints the values the configuration chose to publish, such as a server's public address.
terraform showPrints everything Terraform currently knows about what it manages, in readable form.
terraform state listLists the addresses of everything Terraform is tracking, one per line — the quickest way to see what a configuration owns.
terraform consoleAn interactive prompt for trying out expressions against your real values. Type an expression, see what it evaluates to, change nothing.

Reading a plan: the four symbols

terraform plan marks every proposed change with a symbol in the left margin. Four symbols cover everything you will see, and they are worth learning now because the rest of this page uses them.

SymbolMeaningWhy it happens
+createThe resource is in your configuration but does not exist yet.
-destroyThe resource exists but you removed it from your configuration.
~update in placeThe resource exists but one of its settings differs. The change can be made without deleting anything — for example editing a tag.
-/+replaceA setting differs that cannot be changed on a live resource, so Terraform must destroy it and create a new one. Changing an EC2 instance's ami does this. Read these carefully — the old resource and anything on it is gone.
The last line of every plan is a count: Plan: 1 to add, 0 to change, 0 to destroy. If that line surprises you, do not type yes.

11 · State

What state is, and why Terraform cannot work without it

Your configuration says a server should exist. AWS says a server with ID i-0a1b2c3d4e5f6a7b8 exists. Nothing so far connects the two. Terraform needs a record saying "the block I call aws_instance.web is that specific machine". That record is the state.

By default it is a single file in your working directory called terraform.tfstate, written in JSON. Terraform creates it on the first terraform apply and updates it on every run afterwards.

What it looks like inside

{
  "version": 4,
  "terraform_version": "1.14.8",
  "serial": 3,
  "resources": [
    {
      "mode": "managed",
      "type": "aws_instance",
      "name": "web",
      "instances": [
        {
          "attributes": {
            "id": "i-0a1b2c3d4e5f6a7b8",
            "instance_type": "t3.micro",
            "tags": { "Name": "tflabs-web", "Lab": "lab03" }
          }
        }
      ]
    }
  ]
}
FieldWhat it is for
type + nameThe two labels from your resource block. Together they form the address aws_instance.web.
idThe real identifier AWS assigned. This is the link between your text file and the running machine.
attributesEverything Terraform knew about the resource at the end of the last run — both what you set and what AWS filled in.
serialIncrements on every write. Used to detect two people writing the same state at once.

Three consequences you need to know now

ConsequenceDetail
State is the source of identityDelete the state file and Terraform forgets it ever built anything. Your next plan shows + for everything and apply builds a second copy, while the first keeps running and billing. Back it up; never delete it to "start clean".
State holds secrets in plaintextPlaintext means readable text with no encryption. If a resource has a generated database password, that password is sitting in terraform.tfstate in readable form, even if you marked the variable sensitive. Never commit a state file to git and never put one in a public bucket.
Local state is single-playerThe default file lives on your laptop, so nobody else can see it. Two people running apply against the same infrastructure from two laptops will corrupt each other's work. Teams therefore move state to a shared remote backend — a bucket or service that holds one copy for everyone and locks it during a run. The advanced tier of this track covers that; the basic and intermediate labs all use local state, which is correct for one person learning alone.
State is Terraform's memory of the last run, not a live view of AWS. Keeping the two in agreement is the whole subject of the next section.

12 · Drift

Drift: when reality stops matching the file

Drift is any difference between what your configuration says and what actually exists, caused by something other than Terraform. Someone edits a setting in the web console. An automated script changes a tag. A colleague deletes a resource by hand at 2am to stop an alert. The file did not change; the world did.

Step 1 — the state you applied

You wrote this and ran terraform apply. Terraform created the instance and recorded its ID and attributes in state.

resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id
  instance_type = "t3.micro"

  tags = {
    Name = "tflabs-web"
    Lab  = "lab03"
  }
}

Step 2 — someone changes it by hand

A colleague opens the AWS console, finds the instance, and edits its Name tag from tflabs-web to prod-web-DO-NOT-DELETE. They do not tell you. Three facts now disagree:

SourceValue of the Name tag
Your .tf filetflabs-web — unchanged.
Terraform statetflabs-web — still recording what was true at the last apply.
AWS, right nowprod-web-DO-NOT-DELETE — the only one of the three that is actually true.

Step 3 — plan detects it by refreshing

Before comparing anything, terraform plan refreshes: it asks the provider for the current attributes of every resource in state and updates its in-memory picture. That is the step that finds drift. The plan then reports it in two parts — first what changed outside Terraform, then what Terraform intends to do about it.

aws_instance.web: Refreshing state... [id=i-0a1b2c3d4e5f6a7b8]

Note: Objects have changed outside of Terraform

last "terraform apply" which may have affected this plan:

  # aws_instance.web has been changed

        id            = "i-0a1b2c3d4e5f6a7b8"
      ~ tags          = {
          ~ "Name" = "tflabs-web" -> "prod-web-DO-NOT-DELETE"
        }
        # (28 unchanged attributes hidden)
    }

Terraform used the selected providers to generate the following execution
plan. Resource actions are indicated with the following symbols:
  ~ update in-place

Terraform will perform the following actions:

        id            = "i-0a1b2c3d4e5f6a7b8"

Step 4 — what apply does about it

terraform apply sets the tag back to tflabs-web and updates state. The configuration always wins: Terraform's job is to make reality match the file, so a hand-made change is treated as a mistake to be corrected, not as a new intention to be adopted. If the colleague's change was actually right, the fix is to edit the .tf file and apply that — never to edit the console again.

Drift is why state alone is not enough, and why it works. State remembers what Terraform did; refresh discovers what is true; the configuration says what should be true. The plan is the difference between the last two, expressed as the change needed to satisfy the third.
Not all drift is a cheap fix. If someone changes something that cannot be altered on a live resource, the plan shows -/+ replace instead of ~, and applying it destroys the resource and builds a new one. Always read the symbols before confirming.
